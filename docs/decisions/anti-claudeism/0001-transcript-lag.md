# 0001. transcript 지연 측정 결과, 대응 방안을 채택하지 않기로 했다

2026-08-07

## 결정

transcript 지연으로 편집 경로 목록에서 마지막으로 편집한 파일의 경로가 빠질 수 있다고 판단해
두 가지 대응 방안을 검토했다. 임시 Stop 훅으로 `transcript_path`를 두 번 읽는 동안 지연이 관측되지
않아 둘 다 채택하지 않기로 했다. 훅은 실행될 때마다 `transcript_path`를 한 번만 읽는다.

- PostToolUse로 경로를 미리 적어 두고 Stop 훅에서 읽기
  - 편집 경로 목록을 지연과 무관하게 확보할 수 있지만, 세션별 상태 파일이 생긴다.
  - 훅이 실패하면 이 파일이 남으므로, 남은 파일을 정리하는 로직을 따로 작성해야 한다.
- Stop 훅에서 1초 대기
  - 세션별 상태 파일은 생기지 않지만, 관측되지 않은 지연에 대비해 편집이 있는 모든 턴에서
    훅 종료가 1초씩 늦어진다.

## 배경

`anti_claudeism.py`는 이번 턴에 편집한 파일의 한국어 텍스트를 검사해 Claude 문체 표현을
찾아내는 Stop 훅이다(동작 전반은 [훅 설계](../../architecture/anti-claudeism.md) 참조).

여기서 지연은 Stop 훅이 발동하는 시점에 이번 턴의 마지막 편집이 아직 transcript 파일에
기록되어 있지 않은 상태를 가리킨다. transcript 파일이 비동기로 기록되기 때문이다. 훅 문서는
이를 이렇게 설명한다.

> The transcript file is written asynchronously and may lag the in-memory
> conversation, so it may not yet include the current turn's most recent
> messages when a hook fires.

훅은 편집 경로 목록을 transcript 파일에서 추출한다. 지연이 실재하면 마지막으로 편집한 파일의
경로가 목록에서 빠진다. 훅이 읽는 `tool_use` 블록이 "마지막 사용자 입력 이후"로 한정되므로,
목록에서 빠진 파일을 다시 고치지 않으면 훅이 그 파일을 검사할 수 없다.

## 측정

임시 Stop 훅을 추가하고 이 훅에 전달되는 stdin을 기록했다. 같은 훅이 `transcript_path`를 1초
간격으로 두 번 읽도록 구성하고, 편집 경로 목록과 파일 크기가 달라지는지 확인했다.

- Windows 11, Claude Code 2.1.224 네이티브 바이너리
- 세션 transcript 약 1.6MB, 약 800줄

| 회차 | 턴 구성                         | 편집 수 (1차 → 2차 읽기) | 파일 크기 변화 |
| ---- | ------------------------------- | ------------------------ | -------------- |
| 1    | `Write` 1건, 편집 뒤에 긴 응답  | 1건 → 1건                | 없음           |
| 2    | `Edit` 2건, 편집 뒤에 짧은 응답 | 2건 → 2건                | 없음           |

두 회차 모두 임시 훅이 발동한 시점에 편집이 이미 기록되어 있었고, 1초 사이 파일 크기가
변하지 않았다.

2회차에서는 편집 도구 호출을 턴의 마지막으로 배치하고 이후 응답 텍스트를 줄여, 편집과 Stop
사이 간격이 가장 짧아지도록 구성했다.

## 측정의 한계

- 느린 디스크나 훨씬 큰 transcript는 측정하지 않았다. 표본이 두 건이고 환경도 하나다.
- 한 턴에 편집이 열 건을 넘는 경우는 측정하지 않았다.
- 지연이 나중에 관측되더라도, 편집 경로 목록에서 빠진 파일을 다시 고치면 훅이 그 파일을
  검사하므로 경로 누락은 한 번에 그친다.
