# 0001. transcript 지연을 측정하고 대기를 넣지 않기로 함

2026-08-07

## 결정

지연 대응을 넣지 않는다. `transcript_path`를 한 번 읽고 끝낸다. 두 번 재는 동안 지연이
관측되지 않았다.

검토했다가 버린 것이 둘이다.

- **PostToolUse로 경로를 미리 적어 두고 Stop에서 읽기.** 지연과 무관해지지만 세션별 상태
  파일이 생긴다. 훅이 실패하면 찌꺼기가 남고 그것을 치우는 로직이 다시 붙는다.
- **Stop 훅에서 1초 대기.** 상태는 안 생기지만 편집이 있는 턴마다 1초를 낸다. 관측되지 않는
  현상에 매 턴 비용을 치르는 셈이다.

## 배경

훅 문서는 `transcript_path`가 가리키는 파일을 이렇게 설명한다.

> The transcript file is written asynchronously and may lag the in-memory
> conversation, so it may not yet include the current turn's most recent
> messages when a hook fires.

[설계](../../architecture/ko-style.md)는 이번 턴에 고친 파일 경로를 그 파일에서 얻는다.
지연이 실재하면 마지막 편집이 목록에서 빠지고, 수집이 "마지막 사용자 입력 이후"만 보므로
다음 턴에도 잡히지 않는다. 그 파일을 다시 고치지 않는 한 판정을 영영 건너뛴다.

## 측정

Stop 훅을 임시로 걸고 stdin을 덤프했다. 같은 훅이 `transcript_path`를 1초 간격으로 두 번
읽어, 편집 경로 목록과 파일 크기가 달라지는지 비교했다.

- Windows 11, Claude Code 2.1.224 네이티브 바이너리
- 세션 transcript 약 1.6MB, 약 800줄

| 회차 | 턴의 편집                      | before → after | 파일 크기 |
| ---- | ------------------------------ | -------------- | --------- |
| 1    | `Write` 1건, 뒤에 긴 응답      | 1건 → 1건      | 그대로    |
| 2    | `Edit` 2건, 편집이 마지막 도구 | 2건 → 2건      | 그대로    |

훅이 발동한 시점에 그 턴의 편집이 이미 기록되어 있었고, 1초 사이 파일이 1바이트도 자라지
않았다.

2회차는 편집을 턴의 마지막 도구로 두고 뒤따르는 텍스트를 줄여, 편집과 Stop 사이 간격이 가장
짧은 경우를 만든 것이다.

## 이 측정이 말하지 않는 것

- 표본이 둘이고 환경이 하나다. 느린 디스크나 훨씬 큰 transcript는 재보지 않았다.
- 한 턴에 편집이 열 건 넘게 몰리는 경우는 재보지 않았다.
- 지연이 나중에 관측되더라도 손실은 그 파일 한 번의 판정이다. 다시 고치면 그때 잡힌다.
