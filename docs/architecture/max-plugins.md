# `-max` 플러그인 설계

토큰 여유는 많고 작업 속도가 아쉬운 환경(회사 Max 20 플랜)을 위한 변종. 리뷰를 여러
전문 서브 에이전트에 병렬로 흩뿌려 놓치는 것을 줄이고, 그 대가로 토큰을 아끼지 않는다.
기존 `workflow-core`와 **독립**이며, 둘을 같이 켜지 않는다. 스킬과 에이전트 본문은
한국어로 쓴다 — [0001-max-plugins-in-korean.md](../decisions/0001-max-plugins-in-korean.md).

`github-workflow`·`gitlab-workflow`도 함께 끈다. 둘 다 `workflow-core`에 의존해서, 켜는
순간 `workflow-core`가 따라 켜지고 `review-criteria`가 둘이 된다. 그래서 1단계 동안은
브랜치·PR·MR 워크플로 스킬 없이 리뷰만 쓴다.

```mermaid
flowchart TB
  subgraph core["workflow-core-max"]
    M["메인 에이전트"]
    RC["review-criteria<br/>(팬아웃 오케스트레이션)"]
    A1["항상 도는 리뷰어 7"]
    A2["조건부 리뷰어 1"]
  end

  U([사용자]) <--> M
  M --> RC
  RC --> A1 & A2
  A1 & A2 -.보고.-> RC
  RC --> L[(".refs/review/…<br/>라운드 대장")]
```

## 단계

**1단계는 기존 `workflow-core:review-criteria`와 동등한 역할을 해내는 것까지다.**
판정 기준을 늘리지 않고, 같은 기준을 병렬로 더 촘촘히 적용하는 데만 집중한다. 실제로
써보고 잘 돌아가는 것을 확인한 뒤에 [확장 후보](#확장-후보)로 넘어간다.

산출물은 `workflow-core-max` 플러그인 하나다.

## 요구사항

1. **진행 주도는 메인 에이전트.** 사용자와의 소통, 구현, 커밋, 판단은 전부 메인이
   한다. 서브 에이전트는 읽고 보고만 한다.
2. **작업 단위가 MR에 한정되지 않는다.** git 리포지토리에 변경을 만드는 모든 작업이
   대상이다. "CLAUDE.md 개정"처럼 가벼운 단위도 워킹 트리 안에서 작성-리뷰 사이클을
   완주한 뒤 완성본으로 제시한다. — _2단계_
3. **라운드마다 리뷰를 취합할 채널이 필요하다.** 기존에는 라운드마다 리뷰를 `.refs/`에
   마크다운 문서로 남겼을 뿐, 라운드를 넘어 지적을 추적하는 경로가 아니었다.
4. **리뷰어는 작업 도메인에 따라 달라진다.** 어느 작업에나 도는 공통 리뷰어와, 작업
   형태에 따라 메인이 선택적으로 투입하는 리뷰어를 나눈다. 1단계에서는
   `client-resilience-auditor` 하나가 이 구조의 첫 사례다.

## 플러그인 경계

```
plugins/workflow-core-max/
  .claude-plugin/plugin.json
  skills/
    review-criteria/    팬아웃 오케스트레이션
    refs-scratch/       .refs/ 규약
  agents/               리뷰어 8종
```

켜고 끄는 단위가 플러그인이라, `workflow-core`를 끄면 그쪽 스킬이 전부 같이 꺼진다.
그래서 `-max` 쪽이 필요한 것을 스스로 들고 있어야 한다. `workflow-core`의 나머지 세
스킬은 하나씩 다르게 처리한다.

- **`refs-scratch`는 스킬로 들고 간다.** 라운드 채널이 이 규약 위에 서 있는데, 파일을
  쓰는 주체가 메인 에이전트뿐이라 에이전트 쪽으로 흩을 수가 없다. 트리거로 발동해야
  하므로 스킬로 남는다.
- **`docs-standards`는 분해해 에이전트에 나눈다.** 배치·결정 기록 규칙·산문·주석·참조
  방향은 `docs-intent-auditor`가, "문서 셋 이상이 링을 닫으면 안 된다"는 import 사이클과
  같은 성격이라 `structure-auditor`가 가져간다. 그 결과 `review-criteria` →
  `docs-standards` 강결합이 사라진다.
- **`pre-push`는 싣지 않는다.** 리뷰와 무관하고, 리포지토리당 한 번 훅을 깔면 끝나는
  설치용 스킬이라 없어서 아쉬울 순간이 거의 없다.

`docs-standards`를 분해하면서 **문서를 쓸 때 쓰는 쪽 기능은 잃는다** — "이 문서 어디에
둬야 해?", "ADR 추가". 1단계 목표가 `review-criteria`와의 동등이고 그건 애초에
`review-criteria`의 역할이 아니었으므로 감수한다. 되살릴지는
[#4](https://github.com/nil-park/claude-workflow-kit/issues/4)에서 판단한다.

이 계열은 기존 `workflow-core`와 동기화 장치를 두지 않는다. 따로 진화해도 된다.

## 리뷰 팬아웃

### 대상

기존 `review-criteria`와 같다. 호스팅된 PR/MR, 브랜치, 커밋 전 워킹 디렉터리의 변경분
모두가 대상이고, 마지막 것이 자기리뷰다. 호스팅된 것은 `gh`/`glab`로 diff·설명·논의를
먼저 끌어온 뒤 코드는 로컬 체크아웃에서 읽는다.

수집은 메인이 **한 번만** 한다. 에이전트마다 다시 끌어오면 같은 것을 여러 번 가져오는
데다, 사이에 원격이 바뀌면 축마다 다른 변경을 보게 된다.

### 조율 방식

Anthropic이 정리한 [다섯 가지 조율 패턴](https://claude.com/blog/multi-agent-coordination-patterns)
중 **오케스트레이터-서브에이전트**를 쓴다.
리뷰 축들은 서로 독립이고 상호 의존이 거의 없어서, 이 패턴이 가장 적은 조율 비용으로
맞아떨어진다. 에이전트끼리 서로의 발견을 주고받아야 하는 상황이 아니다.

메인의 역할에서 **검증**이 팬아웃만큼 중요하다. 서브 에이전트는 없는 문제를 지어내며,
여럿을 병렬로 돌리면 그 노이즈도 배수로 늘어난다. 메인은 인용된 `file:line`을 직접 열어
확인하고, **반증을 시도해 살아남은 것만** 대장에 올린다. 이 단계가 없으면 "놓치는 것
없이"가 "쓸 만한 지적을 노이즈에 파묻기"로 뒤집힌다.

### 기준은 어디에 사는가

메인 에이전트가 서브 에이전트에 대해 실제로 아는 것은 **정의의 `description`과 자기가
넘긴 프롬프트뿐**이다. 정의 본문은 그 에이전트의 시스템 프롬프트로 들어갈 뿐 메인에게
보이지 않는다. 그러므로 기준을 전부 본문에 넣으면 메인은 자기가 무엇을 시켰는지 모르는
채로 결과만 받는다.

다만 메인이 기준을 알아야 하는 이유가 검증은 아니다. 검증은 인용된 코드를 직접 읽어
판단하므로 기준을 몰라도 된다. 메인에게 기준이 필요한 곳은 **투입할 에이전트를 고를
때**, **무엇이 검사되지 않았는지 알아야 할 때**(빈 라운드가 "문제 없음"인지 "아무도 안
봄"인지 구분해야 사이클을 끝낼 수 있다), 그리고 **사용자에게 적용 기준을 설명할 때**다.

그래서 **"무엇을"은 스킬, "어떻게"는 에이전트**로 가른다.

| 사는 곳                       | 담는 것                                                           |
| ----------------------------- | ----------------------------------------------------------------- |
| `review-criteria`의 팬아웃 표 | 각 에이전트의 책임 범위 — 무엇을 보고, 무엇을 **안 보는지**       |
| 에이전트 `description`        | 같은 범위를 한 문장으로. 메인에게 목록으로 주입되는 이중 안전장치 |
| 에이전트 본문                 | 그 범위 안에서 어떻게 깊게 파는지 — 기법, 체크리스트, 출력 포맷   |

여기에 런타임 안전장치를 하나 건다. **각 에이전트는 보고 말미에 자신이 적용한 기준과
범위 밖이라 보지 않은 것을 함께 반환한다.** 메인은 정의 파일을 읽지 않고도 실제 검사
범위를 확인할 수 있고, 정의가 바뀌었는데 스킬 표가 따라오지 않은 드리프트도 여기서
드러난다.

### 리뷰어 (1단계)

기존 `review-criteria`의 판정 항목을 그대로 여덟으로 분해한 것이다. 새 기준을 더하지
않는다. "안 본다"가 표의 절반인 이유는 축이 겹치면 같은 지적이 여러 번 올라와 메인의
검증 비용만 배로 늘기 때문이다.

| 에이전트                    | 본다                                                                                                                            | 안 본다                                                                                                                 |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `correctness-hunter`        | 경계·off-by-one, 빈/부재 입력, 잘못된 변수, 미처리 에러 경로, 상태·순서 가정, 뮤테이션 앨리어싱, 동시성 경합, 논리 반전         | 스타일, 성능, 테스트 유무, 문서. 에러 억제는 그 자체로는 넘기고 버그를 만들 때만 본다                                   |
| `resource-auditor`          | 메모리 누수, 해제되지 않는 자원(파일·소켓·커서), 불필요한 재계산·중복 조회, 자료구조 오용                                       | 재시도 정책, 정확성 버그, 근거 없는 마이크로 최적화 제안                                                                |
| `silent-failure-hunter`     | `# type: ignore`·`# noqa`·bare `except`·빈 catch, 로깅 없이 삼키는 실패, 문제를 가리는 폴백·기본값 반환                         | 억제가 정당한 경우(외부 라이브러리 오탐 등), 에러 메시지 문구 품질                                                      |
| `test-auditor`              | 아무것도 검증하지 않는 테스트, 구현을 그대로 베낀 단정, diff가 새로 만든 분기 중 아무도 실행하지 않는 것                        | 커버리지 수치, 테스트 스타일, diff 밖 코드에 대한 테스트 요구                                                           |
| `hygiene-auditor`           | 디버그 출력, 주석 처리된 코드, 도달 불가 코드, 스트레이 TODO, 주변 코드와 어긋나는 스타일·네이밍                                | 리포지토리 전체 스타일 규약 변경 요구, 문서·주석 내용, 버그                                                             |
| `docs-intent-auditor`       | PR/MR 설명이 실제 diff와 맞고 충분한지, 링크된 문서와의 불일치, diff가 건드린 문서의 배치·산문·결정 기록 규칙, 주석과 참조 방향 | diff가 건드리지 않은 문서의 자체 품질(불일치의 근거로 읽기만 한다), 리포지토리 전체 문서 구조 재편, 기존 관례 변경 요구 |
| `structure-auditor`         | diff가 추가한 import가 사이클을 닫는지, 모듈 경계 침범                                                                          | 전체 의존성 그래프 감사, 디렉터리 배치·파일명, 아키텍처 재설계 제안                                                     |
| `client-resilience-auditor` | 일시적 실패에 재시도가 붙었는지, 백오프의 합리성(지터 포함), 시도 횟수 상한, 비멱등 연산에 잘못 붙은 재시도, 타임아웃 부재      | 서버 측 복원력, 커넥션 풀, 성능 튜닝                                                                                    |

`client-resilience-auditor`만 조건부다 — HTTP/RPC/외부 서비스 클라이언트가 변경될 때만
투입한다. 나머지 일곱은 항상 돈다.

`docs-intent-auditor`는 채우기 쉬운 축이라 잡소리가 잘 나온다. 정의 본문에서 "읽기
정말 어렵거나 곧 낡을 것만 지적하라"를 못 박는다.

### 라운드 채널

`.refs/` 아래 파일로 한다.

```
.refs/review/<작업-슬러그>/
  r1/, r2/, …      라운드마다 하나씩
    <agent>.md     각 에이전트가 낸 원본 보고
    verdict.md     메인이 검증을 마치고 확정한 라운드 결과
  ledger.md        라운드를 넘어 지속되는 지적 대장 (open/fixed/rejected/deferred)
```

**파일은 메인이 쓴다.** 서브 에이전트에 `Write`를 주면 소스를 고칠 수 있게 되고, 어차피
메인이 모든 지적을 검증하느라 다 읽어야 하므로 컨텍스트 절약도 되지 않는다. 서브
에이전트는 읽기 전용으로 두고 기본 반환 경로로 보고한다.

따라서 이 채널의 목적은 컨텍스트 절약이 아니라 **라운드를 넘는 지속성과 사용자 감사
가능성**이다. `ledger.md`가 있어야 3라운드에서 기각한 지적을 5라운드가 다시 올릴 때
알아볼 수 있다.

### 채택하지 않은 것

| 대안                  | 왜 안 쓰는가                                                                                                                                                                                     |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| SQLite 등 로컬 DB     | 라운드당 지적 수십 건 규모에 질의 능력이 필요 없다. 의존성과 스키마 관리 비용만 남는다                                                                                                           |
| Agent Teams           | 실험 기능이라 환경 변수로 켜야 하고, 서브 에이전트 정의의 `skills` 필드가 팀원에게 적용되지 않아 스킬 기반 설계가 깨진다. 세션 재개도 안 된다. 무엇보다 팀원 간 직접 대화가 필요한 문제가 아니다 |
| MCP 메시지 버스 / A2A | 조직 간·벤더 간 에이전트 연결용 규격. 한 세션 안의 독립 축 몇 개에는 과하다                                                                                                                      |
