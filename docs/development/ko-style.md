# ko-style 훅의 전제와 검증

[설계](../architecture/ko-style.md)의 바탕이 되는 사실과, 그것을 확인하는 방법이다.

## Stop 훅이 받는 것

stdin으로 오는 JSON은 이게 전부다.

| 필드                     | 내용                                                                         |
| ------------------------ | ---------------------------------------------------------------------------- |
| `session_id`             | 세션 식별자                                                                  |
| `prompt_id`              | 처리 중인 사용자 프롬프트의 UUID. v2.1.196 이상에서 오고 첫 입력 전에는 없다 |
| `transcript_path`        | 대화 JSONL 경로. 비동기로 쓰여 이번 턴의 마지막 메시지가 아직 없을 수 있다   |
| `cwd`                    | 세션을 시작한 디렉터리. 프로젝트 루트라는 보장은 없다                        |
| `permission_mode`        | 권한 모드                                                                    |
| `effort`                 | 이번 턴의 effort 레벨                                                        |
| `hook_event_name`        | `"Stop"`                                                                     |
| `stop_hook_active`       | 훅 때문에 이어지는 턴이면 `true`                                             |
| `last_assistant_message` | 마지막 응답 텍스트                                                           |
| `background_tasks`       | 진행 중인 백그라운드 작업                                                    |
| `session_crons`          | 세션에 걸린 예약 실행                                                        |

이번 턴에 고친 파일의 목록은 없다.

환경변수로는 `CLAUDE_PROJECT_DIR`이 온다. 프로젝트 루트를 가리키지만 구분자가 입력의 `cwd`와
다르다. Windows에서 `CLAUDE_PROJECT_DIR`은 `C:/Git/...`, `cwd`는 `C:\Git\...`이었다. 두 값을
비교하거나 상대경로를 만들 때는 정규화해야 한다.

`CLAUDE_PLUGIN_ROOT`와 `CLAUDE_PLUGIN_DATA`는 플러그인으로 배포된 훅에만 온다.

## 실행 환경

- 훅은 `python3`라는 이름으로 실행된다. `hooks.json`에는 커맨드를 한 줄로만 적을 수 있어
  OS별로 이름을 갈라 쓸 자리가 없다.
  - python.org 인스톨러로 설치한 Windows에는 `python3.exe`가 없다. pyenv-win과 Microsoft
    Store 배포판에는 있다.
- 그 `python3`는 3.11 이상이어야 한다. 표준 라이브러리 밖의 것은 쓰지 않는다.
  - Debian 12와 Ubuntu 24.04는 그대로 만족한다. macOS의 기본 파이썬은 3.9라 따로 깔아야
    한다.
- 훅은 남의 시스템 `python3`로 직접 실행된다. uv도 가상환경도 거치지 않으므로 이 리포의
  개발 도구는 훅이 도는 환경에 없다.
- `workflow-core:coding-standards`의 200줄 규칙은 훅 스크립트에 적용하지 않는다.
- 한국어 텍스트가 언제나 UTF-8인 것은 아니다. Windows에서 만든 문서는 CP949로 저장되어
  있기도 하다.
- Python의 텍스트 stdout은 UTF-8이 기본이 아니다. Windows에서는 로케일 코드페이지를 쓰고,
  한국어 Windows에서 그것은 CP949다.
- pyenv를 쓰는 환경에서는 작업 중인 프로젝트의 `.python-version`이 어느 파이썬을 부를지
  정한다. 거기 적힌 버전이 pyenv에 없으면 훅이 실행되지 못하고, 훅이 안 도는 것은 겉으로
  드러나지 않는다.

## 플랫폼이 정한 것

- API 에러로 끝난 턴에서는 `StopFailure`가 대신 발동하고 그 출력과 종료 코드는 무시된다.
- 훅이 stdout으로 내보낸 바이트는 UTF-8로 읽힌다. 훅 문서에는 인코딩 얘기가 없고 실측으로
  확인했다.
  - 디코드에 실패한 바이트는 U+FFFD로 바뀌고 JSON 파싱은 그대로 성공한다. cp949로 내보내면
    오류 하나 없이 한글만 죽은 채 보고가 도착한다.
- 훅이 내보내는 문자열은 `additionalContext`를 포함해 10,000자에서 잘린다. 넘으면 파일로
  저장되고 미리보기와 경로로 대체된다.
- Claude Code는 훅이 8회 연속으로 막으면 무시하고 턴을 끝낸다. 이 훅은 두 번째 Stop을
  통과시키므로 그 상한까지 가지 않는다.
- 훅은 탐지 결과를 Claude가 한 번 읽는 것까지만 보장한다. 지적을 읽고 아무것도 고치지 않은
  채 턴을 끝낼 수 있다.
- Bash로 고친 파일은 탐지되지 않는다. `tool_use` 입력에 경로가 없고 명령 문자열만 있다.
  - `sed -i`, `cat > f <<EOF`, 스크립트가 안에서 쓰는 파일이 모두 여기 해당한다. 그 파일을
    나중에 `Write`나 `Edit`으로 건드리면 그때 검사된다.

## 판정의 한계

- 1MB를 넘는 파일은 검사되지 않는다. 사람이 읽는 문서는 그만큼 커지지 않는다.
- `ko-style-dictionary.json`이라는 이름을 쓰는 파일은 사전이 아니어도 검사되지 않는다.
- 사전 매칭은 앞뒤 문맥을 보지 않는다.
  - 예를 들어 `소비자`가 consumer의 직역으로 등재되어 있으면, 미국 경제를 다루는 문서에서
    `소비자`를 써도 탐지된다.
- 사전이 커질수록 오탐이 늘어난다. 탐지된 표현은 오탐이라도 Claude가 그 자리에서 직역인지
  판단해야 하므로, 사전 크기는 그대로 매 턴의 검토 비용이 된다.
- 사전에 없는 표현은 탐지되지 않는다. 사전은 실제로 틀렸던 것만 담는다.
- 플러그인과 함께 배포되는 사전은 갱신될 때 통째로 교체된다. 거기에 직접 적은 것은 남지
  않는다.
- `term`이 짧을수록 다른 단어에 파묻힌다. 경계를 걸지 않으면 `축`은 `축소`·`건축`·`압축`에
  전부 걸린다.
- 용언은 어간과 어미가 한 음절로 합쳐져서 어절 경계를 걸 수 없다.
  - `되어지다`는 `되어진다`에서 `되어진`, `되어졌다`에서 `되어졌`이 된다. 공통 접두는
    `되어`뿐이고, 그것은 `되어서`·`되어야`에도 걸린다.
- 이중 피동이라고 다 틀린 것은 아니다. `알려지다`, `밝혀지다`, `이루어지다`는 표준이다.
  `-어지다`로 끝나는 말을 한꺼번에 잡으면 이것들까지 탐지되므로, 틀린 것을 하나씩 등재한다.

## 전제를 다시 확인하는 방법

입력 필드 표는 stdin을 그대로 파일에 쓰는 Stop 훅을 임시로 걸고 한 턴을 돌려서 얻은 것이다.
표를 다시 확인하려면 같은 방법을 쓴다. 프로젝트 `.claude/settings.local.json`에 걸면 그
리포에서만 돈다.

훅을 건 뒤에는 `/hooks`로 등록됐는지 먼저 본다. `0 hooks configured`로 나오면 그 세션은
훅을 모르는 것이므로 `claude --resume`으로 다시 켠다. 세션 도중에 `.claude/settings.local.json`을
새로 만든 경우가 여기 해당한다. 훅 문서는 설정 파일의 훅을 고치면 파일 워처가 집는다고
하지만, 없던 파일을 만드는 것은 집히지 않았다. 훅이 안 도는 것은 겉으로 드러나지 않으므로
등록을 확인하기 전에는 측정 결과를 믿지 않는다.

transcript 지연은 [0001](../decisions/ko-style/0001-transcript-lag.md)에서 쟀다. 다시 재려면
덤프한 `transcript_path`를 1초 간격으로 두 번 읽어 편집 목록과 파일 크기를 비교한다.

stdout 인코딩은 같은 한글을 UTF-8 바이트와 cp949 바이트로 한 문자열에 나란히 담아 보내고,
도착한 쪽의 코드포인트를 후보 디코딩과 맞춰서 쟀다. ASCII만 담은 대조군을 먼저 한 번 보내
훅이 실제로 붙어 있는지부터 가른다.

훅 호출 비용은 훅을 하위 프로세스로 여러 번 띄워 벽시계로 재고, 같은 횟수로 잰 인터프리터
기동 시간을 따로 두어 가른다. 판정 비용은 파일 크기가 아니라 탐지 건수를 따라가므로, 줄마다
걸리는 파일을 만들어 함께 잰다.
