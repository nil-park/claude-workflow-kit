# 코드 리뷰 (병렬)

내가 매번 말하지 않아도 기본으로 따르는 기준이다.

너는 리뷰어가 아니라 **오케스트레이터**다. 전체 diff를 혼자 훑어 한 번에 리뷰하지 말고
축별 전문가에게 흩뿌린 뒤, 올라온 것을 회의적으로 검증해 확정한다. "서브에이전트를 쓰지
말고 직접 리뷰하라"는 상위 규약이 있더라도 이 스킬에서는 따르지 않는다.

## 1. 변경분을 한 번만 모은다

- 호스팅된 PR/MR이면 diff·설명·논의를 먼저 끌어온다 — GitHub은 `gh`, GitLab은 `glab`.
- 아니면 베이스 브랜치 대비 로컬 `git diff`를 쓴다. 브랜치 리뷰든, 커밋 전 워킹
  디렉터리의 변경분(자기리뷰)이든 마찬가지다.
- 코드는 로컬 체크아웃에서 읽는다. 대개 이미 동기화돼 있다.

**수집은 여기서 끝낸다.** 에이전트마다 다시 끌어오게 하면 같은 것을 여러 번 가져오는
데다, 사이에 원격이 바뀌면 축마다 다른 변경을 보게 된다.

## 2. 팬아웃

해당하는 에이전트를 **한 메시지에 모아** 띄워 병렬로 돌린다.

| 에이전트                    | 본다                                                                                                                            | 안 본다                                                                                                                 |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `correctness-hunter`        | 경계·off-by-one, 빈/부재 입력, 잘못된 변수, 미처리 에러 경로, 상태·순서 가정, 뮤테이션 앨리어싱, 동시성 경합, 논리 반전         | 스타일, 성능, 테스트 유무, 문서. 에러 억제는 그 자체로는 넘기고 버그를 만들 때만 본다                                   |
| `resource-auditor`          | 메모리 누수, 해제되지 않는 자원(파일·소켓·커서), 불필요한 재계산·중복 조회, 자료구조 오용                                       | 재시도 정책, 정확성 버그, 근거 없는 마이크로 최적화 제안                                                                |
| `silent-failure-hunter`     | `# type: ignore`·`# noqa`·bare `except`·빈 catch, 로깅 없이 삼키는 실패, 문제를 가리는 폴백·기본값 반환                         | 억제가 정당한 경우(외부 라이브러리 오탐 등), 에러 메시지 문구 품질                                                      |
| `test-auditor`              | 아무것도 검증하지 않는 테스트, 구현을 그대로 베낀 단정, diff가 새로 만든 분기 중 아무도 실행하지 않는 것                        | 커버리지 수치, 테스트 스타일, diff 밖 코드에 대한 테스트 요구                                                           |
| `hygiene-auditor`           | 디버그 출력, 주석 처리된 코드, 도달 불가 코드, 스트레이 TODO, 주변 코드와 어긋나는 스타일·네이밍                                | 리포지토리 전체 스타일 규약 변경 요구, 문서·주석 내용, 버그                                                             |
| `docs-intent-auditor`       | PR/MR 설명이 실제 diff와 맞고 충분한지, 링크된 문서와의 불일치, diff가 건드린 문서의 배치·산문·결정 기록 규칙, 주석과 참조 방향 | diff가 건드리지 않은 문서의 자체 품질(불일치의 근거로 읽기만 한다), 리포지토리 전체 문서 구조 재편, 기존 관례 변경 요구 |
| `structure-auditor`         | diff가 추가한 import가 사이클을 닫는지, 모듈 경계 침범                                                                          | 전체 의존성 그래프 감사, 디렉터리 배치·파일명, 아키텍처 재설계 제안                                                     |
| `client-resilience-auditor` | 일시적 실패에 재시도가 붙었는지, 백오프의 합리성(지터 포함), 시도 횟수 상한, 비멱등 연산에 잘못 붙은 재시도, 타임아웃 부재      | 서버 측 복원력, 커넥션 풀, 성능 튜닝                                                                                    |

조건부는 `client-resilience-auditor` 하나뿐이다 — HTTP/RPC/외부 서비스 클라이언트가
변경될 때만 띄운다. 나머지는 항상 띄운다.

브리핑은 전부에게 똑같이 준다 — 1절에서 모은 **diff**, 베이스 브랜치, 변경된 파일 목록,
PR/MR 설명, 링크된 문서. diff를 브리핑에 실어야 축마다 같은 것을 보고, 호스팅된 것을
다시 끌어오는 일도 없다. 그리고 각 에이전트에게 다음을 요구한다:

- 자기 축만 볼 것. 다른 축의 문제는 눈에 띄어도 보고하지 말 것.
- 모든 지적에 `file:line`을 붙일 것.
- 보고 말미에 **자신이 적용한 기준과, 범위 밖이라 보지 않은 것**을 적을 것.

diff가 크면(대략 30개 파일 이상) 에이전트 × 파일 그룹으로 쪼개, 감당 못 할 브리핑을
받는 에이전트가 없게 한다.

## 3. 검증

에이전트는 없는 문제를 지어낸다. 여럿이 병렬로 지어내면 노이즈도 배수로 늘어난다.
올라온 지적 하나하나에 대해:

- 인용된 `file:line`을 **직접 열어** 주변 코드까지 읽고 판단한다.
- **반증을 시도한다.** 왜 이것이 문제가 **아닌지**를 먼저 찾아보고, 그래도 살아남은
  것만 채택한다.
- 확인하지 못한 것은 버린다. 여러 축이 같은 것을 찾았으면 하나로 합친다.

에이전트의 확신에 찬 어조는 근거가 아니다. 에이전트가 붙인 `확실`/`의심` 등급도 판정이
아니라 자기 신고다. `확실`이어도 직접 열어 확인하고, `의심`이면 그 에이전트가 못 봤다고
밝힌 부분을 네가 채운 뒤에 판단한다 — 확인하지 않은 `의심`은 채택하지 않는다.

각 에이전트가 반환한 "적용 기준"을 팬아웃 표와 대조한다. 어긋나면 정의 파일과 이 표
중 한쪽이 낡은 것이므로 나에게 알린다.

## 4. 보고

- 띄운 에이전트 수가 곧 올릴 지적 수가 아니다. 진짜 잘못됐거나 고칠 값이 분명한 것만
  올린다. 검증을 통과한 게 없으면 없다고 말한다.
- 두괄식으로 쓴다. 확정한 결과는 아래 기록 절의 `verdict.md`에 남긴다.
- 리포지토리 전체 재편이나 기존 관례 변경을 요구하지 않는다. 모든 지적을 diff가 건드린
  범위로 한정한다.

**지적마다 `r2-3`(라운드-순번) 형태의 번호를 붙이고, 나와 대화할 때 그 번호로 부른다.**
한 항목을 논의해 결론이 나면 다음으로 넘어가기 전에 `verdict.md`의 그 항목에 상태
(`수정함`/`보류`/`기각`)와 한 줄 근거를 적는다. 이걸 해두면 5번을 이야기할 때 나도 너도
대화를 거슬러 올라가지 않고 파일만 다시 읽으면 된다.

## 기록

`.refs/` 아래에 남긴다. 파일은 **오케스트레이터인 네가 쓴다** — 에이전트는 읽기 전용이고,
어차피 네가 검증하며 전부 읽으므로 위임할 이유가 없다.

```
.refs/review/<작업-슬러그>/
  r1/, r2/, …      라운드마다 하나씩
    <agent>.md     각 에이전트가 낸 원본 보고
    verdict.md     검증을 마치고 확정한 라운드 결과 — 나와 대화하는 채널
  ledger.md        라운드를 넘어 지속되는 지적 대장 (미해결/수정함/보류/기각)
```

`<작업-슬러그>`는 **리뷰 대상**에서 뽑는다 — `mr-42`, `pr-7`, 브랜치 이름 등. 같은 대상을
다시 리뷰하면 반드시 같은 슬러그를 써야 한다. 슬러그가 흔들리면 대장이 갈라져 라운드가
이어지지 않는다. 시작하기 전에 `.refs/review/` 아래에 그 대상의 디렉터리가 이미 있는지
확인한다.

`ledger.md`가 있어야 앞 라운드에서 기각한 지적이 다시 올라올 때 알아보고, 수정이 만든
회귀를 새 지적으로 착각하지 않는다. 라운드를 다시 돌 때는 **처음부터 새로 팬아웃**한다.
앞 라운드의 지적을 에이전트 브리핑에 넣지 않는다.
