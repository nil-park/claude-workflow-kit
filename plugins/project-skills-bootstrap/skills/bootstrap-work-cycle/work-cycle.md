# 적용 대상

- 파일을 만들거나 고치는 작업은 크기와 무관하게 모두 이 사이클에 따라 진행한다.
  - 예를 들어 "CLAUDE.md 한 줄 고쳐줘"도 대상이다.
  - 나에게는 사이클을 완주해 완결된 결과물을 제시한다.
- 리뷰 라운드의 대상은 작업에 따라 다르다.
  - 설계: 설계 문서
  - 구현: 구현 변경분
  - 이슈와 PR/MR: 제목과 설명
- 파일을 남기지 않는 작업은 대상이 아니다.
  - "장애 원인을 로그에서 찾아줘" (읽기만 한다)
  - "도커 이미지랑 볼륨 정리해줘" (파일을 고치지 않는다)

## git 리포지토리 밖의 파일

- `~/.claude/CLAUDE.md`, 홈 디렉터리의 스크립트, 시스템 설정도 대상이다.
- git으로 되돌릴 수 없으므로, 고치기 전에 같은 디렉터리에 `.bak` 확장자를 붙인 사본을 만든다.
  - 리뷰 라운드에서는 원본과 사본의 차이를 diff로 검토한다.

## 도메인 판정

- 리뷰 기준은 도메인에 따라 달라지므로, 작업을 시작하기 전에 나와 합의한 작업 단위에서 도메인을 유추해 판정한다.
  - 문서 개정, 애플리케이션 코드, 인프라 코드 중 무엇인지
  - 어떤 언어, 런타임, 프레임워크를 사용하는지
  - 클라이언트, 서버, 배치 작업 중 무엇인지

# `docs-standards`와 `coding-standards` 원문 확인

- 두 스킬의 조항은 원문에서 확인한다.
  - 이전 턴이나 라운드 기록에 적어 둔 요약본으로 원문을 대신하지 않는다.
  - 요약본에는 목적과 예외 조건이 빠지므로, 남은 제한 사항만 기계적으로 확인하게 된다.
- 작성 단계와 리뷰 라운드 모두에서, 기준을 적용하기 직전에 해당 조항을 다시 읽는다.
- 이 규칙은 나에게 하는 보고에는 적용하지 않는다.
  - 보고는 계속 요약해서 전한다.

# 리뷰 라운드

- **서브 에이전트나 빌트인 스킬을 사용하지 않고 네가 직접 리뷰한다.**
  - 지적 사항도 네가 직접 고친다.
- **지적이 없는 라운드(클린 패스)가 세 번 연속 나올 때까지 반복한다.**
  - 지적이 나온 라운드가 있으면 연속 횟수를 0으로 되돌린다.
  - 라운드 수에는 상한이 없다.
- 문서를 작성하거나 고친 작업은 `docs-standards` 스킬의 기준으로 리뷰한다.
  - 라운드마다 배치 표에서 해당 문서의 행을 찾아, 문서 내용을 그 행의 넣을 것과 뺄 것에 대조한다.
  - 상세 규칙은 문서 종류마다 적용 범위가 정해져 있으므로, 해당하는 규칙을 전부 확인한다.
    - 코드 리뷰처럼 기준을 골라 나눠 보지 않는다.
- 코드를 작성하거나 고친 작업은 `coding-standards` 스킬의 기준으로 리뷰한다.
  - 라운드마다 도메인과 작업 단위에 맞는 리뷰 기준을 스킬에서 5개 골라 리뷰한다.
    - 해당하는 기준을 모두 한 번씩 고르기 전에는 이미 고른 기준을 다시 고르지 않는다.
    - 가능하면 스킬에 없는 관점으로도 확인한다.
  - 단, 고른 기준과 별개로 **네가 작성하거나 고친 코드가 다른 곳에 문제를 일으키지 않았는지** 라운드마다 확인한다.
  - 기준끼리 충돌해 같은 곳을 되돌려 고치는 회귀 루프가 생기지 않는지 반드시 살핀다.
    - 루프가 보이면 이번 라운드의 기준만 기계적으로 적용하지 말고, 충돌하는 기준을 함께 만족하는 해법을 찾는다.
- 대용량 파일이 아니면 `grep` 등으로 발췌하지 않고 **파일 전체를 직접 읽는다**.
- 라운드 결과는 나에게 매번 보고하지 않고, 임시 디렉터리에 마크다운 문서로 기록한다.
  - 라운드마다 새 문서를 만들어도 되고, 기존 문서에 덧붙여도 된다.
  - 나는 주로 최종 보고의 요약을 확인하고, 라운드 기록은 필요할 때만 참조한다.
- 리뷰 라운드를 반복하는 동안에는 아래 세 경우에만 나를 부른다.
  - 설계를 바꿔야만 해결되는 문제가 나왔을 때
  - 작업 범위를 넓혀야만 해결되는 문제가 나왔을 때
  - 설계가 구체적이지 않아 가정을 너무 많이 해야 할 때
