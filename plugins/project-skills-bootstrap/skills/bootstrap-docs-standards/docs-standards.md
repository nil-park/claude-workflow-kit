# 문서와 주석 기준

## 배치

- **리포지토리에 디렉터리 이름 규약이 있으면 그것을 따른다.**
  - 아래 표는 문서를 놓을 디렉터리가 정해져 있지 않을 때의 기본값이다.
  - 규약이 문서로 적혀 있지 않아도 해당하는 디렉터리가 이미 있으면 규약이 있는 것으로 간주한다.
  - 내가 문서 구조 개편을 지시하지 않는 한, 너는 기존 이름 규약을 바꾸자고 제안하지 않는다.
- 이미 있는 디렉터리 이름이 표와 다르면, 각 행의 내용과 규칙을 성격이 가장 비슷한 디렉터리에 적용한다.
  - 예를 들어 `docs/architecture/` 대신 `docs/spec/`이 있다면 그 디렉터리에서 why에 해당하는
    서술을 모두 뺀다.

| 위치                 | 내용                                                                          | 넣을 것                | 뺄 것     |
| -------------------- | ----------------------------------------------------------------------------- | ---------------------- | --------- |
| `docs/requirements/` | SRS. 유스케이스 및 사용자 시나리오. 요구사항 항목당 한 줄 설명                | who, what, when, where | how, why  |
| `docs/architecture/` | **애플리케이션 및 시스템의 이상적인 형상.** 구현을 추상화한 서술. 인프라 구성 | **what**, how          | **why**   |
| `docs/decisions/`    | 결정 기록. 내가 명시적으로 요청할 때만 쓴다.                                  | why, analysis          |           |
| `docs/runbook/`      | 배포 절차, 수작업이 필요한 처리, 장애 대응 절차                               | how                    | **why**   |
| `docs/setup/`        | 개발 환경 구축                                                                | how, what              | why       |
| `docs/development/`  | **전제와 가정**, 개발과 검증 방법. 스모크 테스트, FMEA                        | how, what              |           |
| `docs/monitoring/`   | 알람과 모니터링. 어떤 지표를 어떻게 보는지                                    | how, what, why         |           |
| `docs/reference/`    | 외부 플랫폼·라이브러리를 조사해 남긴 참고 자료                                | what                   | why       |
| `docs/experiments/`  | 개발을 시작하기 전에 수행한 실험 내용                                         | what, how              |           |
| 이슈 설명            | 이슈 카테고리에 따라 자율적으로 쓴다                                          | 5W1H                   |           |
| PR/MR 본문           | 무엇이 달라지는지, 어떻게 적용하는지, what, how, why 순서로                   | what, how, why         | 구현 상세 |
| 소스 코드 주석       | 자명하지 않은 짧은 why                                                        | why                    | what      |

## 상세 규칙

- ⚠️**architecture에 절대 why를 넣지 않는다**⚠️
  - 이 원칙이 제일 중요하다.
  - 한 절이 전부 근거로 채워져 있으면 문장을 다듬지 말고 그 절 전체를 지운다.
- **문서를 고칠 때에는 덧붙이는 쪽보다 빼는 쪽을 먼저 검토한다.**
  - 내용을 지워도 구현체의 의도를 읽을 수 있으면 지운다.
  - 어떤 서술을 지웠다고 가정하고, 회귀 오류가 발생할 가능성과 폐기한 대안을 다시 채택할 가능성이 모두 낮으면 실제로 지운다.
- **development 문서의 가장 중요한 기능은 "전제"를 넣는 것**이다.
  - 전제를 문서에 명확히 밝히면 방어 로직으로 처리해야 할 엣지 케이스가 줄어든다.
    - 설계와 구현의 복잡도를 키우는 주된 원인이 그 방어 로직이다.
  - 우리가 정한 것뿐 아니라 외부 플랫폼·라이브러리로 인한 제약도 전제다.
  - reference에는 조사한 사실만 적는다.
- 여러 문장에 걸쳐 서술해야 하는 why는 PR/MR 본문의 맨 아래에 별도 절로 모으고 what과 섞지 않는다.
  - 문서나 코드에서 근거가 필요하면 PR/MR, 이슈, 또는 decisions 문서로 링크를 건다.
  - monitoring은 특정 지표를 봐야 하는 이유가 가까이 있어야 하므로 예외다.
- decisions에는 시점이 고정된 실측 데이터를 위주로 쓰고, 그 데이터에 근거한 결정 사항은 간결하게 적는다.
- 대시보드와 알림 채널이 어디 있는지는 monitoring에서 찾고, 알림이 울렸을 때 문제를 어떻게 해결할지는 runbook에서 확인한다.
- PR/MR에서 **시점 고정값(특히 테스트 수량), 체크박스, 후속 작업을 전부 제거한다.**
  - 작업이 아직 완료되지 않았어도 완성될 시점을 기준으로 쓴다.
- PR/MR 본문의 how는 독자가 이 변경 때문에 해야 할 일이다.
  - `terraform apply`, 마이그레이션 명령, 바꿔야 할 설정이 여기 들어간다.
  - 구현 방식은 diff에 이미 드러난다.
  - 구현 방식까지 본문에 적으면 정작 기능 변경이 눈에 띄지 않는다.
- PR/MR 본문의 what은 5줄을 목표로 한다.
  - 맨 아래 why 절은 이 계산에 넣지 않는다.
- PR/MR 본문의 헤딩에 What, How, Why를 그대로 쓰지 않는다.
  - 한글 추천: "변경 사항", "적용 방법", "배경", "제약 사항"
  - 영문 추천: "Summary", "Changes", "How to apply", "Background"
  - 불필요한 절은 쓰지 않는다.
  - "적용 방법" 절에는 독자가 해야 할 자명하지 않은 것만 넣는다.
- 디렉터리와 파일의 이름은 독자가 그것만 보고 원하는 문서를 찾을 수 있게 짓는다.
- **what과 how는 중요한 것을 앞에 놓고, 불릿과 하위 불릿으로 계층을 나눈다.**
  - 한 항목이 길어지면 요지를 상위 한 줄로 올리고 나머지를 하위 불릿으로 내린다.
  - 아래에 있는 다이어그램·표·예시 규칙이 이 조항보다 우선한다.
  - why에도 불릿 계층화를 지향하되, 반드시 그렇게 해야 하는 것은 아니다.
- **다이어그램, 표, 예시**로 보여 주는 편이 산문보다 나으면 그 형식을 쓴다.
- 강조 표기(bold, italic)는 독자가 반드시 읽어야 할 정보에만 쓴다.
  - 남발하면 강조가 희석된다.
- 한 문장은 100자를 넘기지 않는다.
  - 100자를 넘으면 문장을 나누거나 하위 불릿으로 내린다.
- 같은 것을 문서마다 다르게 부르지 않는다.
- 뜻이 다른 둘에 같은 용어를 쓰지 않는다.
- 한국어 문장이 성립하는지 검토한다.
  - 맞춤법, 띄어쓰기, 조사, 서술어 없이 끝나는 문장, 주어와 서술어의 호응, 행위 주체 누락, 목적어 누락, 한국어 화자가 쓰지 않는 번역투를 확인한다.
  - 가운뎃점은 같은 층위의 낱말을 나열할 때만 쓴다.
    - 서술구나 절을 이으면 `와/과`나 쉼표를 쓴다.
  - 줄표는 문장 중간에 끼우는 짧은 부연에만 쓴다.
    - 예시를 열거하거나 뒷말을 이을 때는 쉼표나 괄호를 쓰거나 문장을 끊는다.
    - 낱말과 그 뒤의 조사 사이에는 줄표를 끼우지 않는다.
  - 일반적인 동사가 있는 자리에 비유적인 낱말을 쓰지 않는다.
  - 문서의 헤딩, 표의 셀, 목록 항목, PR/MR의 제목은 명사구로 끝나도 된다.
- 한국어 검수 대상에는 문서, 주석, 이슈, PR/MR 본문 외에 화면 문구, 오류 메시지, 테스트 이름, 커밋 메시지도 포함된다.
  - 웹 클라이언트나 앱 화면 등 엔드 유저가 보는 문구에 개발자만 아는 용어를 쓰지 않는다.
  - 주석의 문장을 고친 뒤에는 해당 주석이 코드와 어긋나지 않는지 재확인한다.
- 원본이 이 리포에 있는 코드는 문서에 붙여넣지 않는다.
  - 넣을 수 있는 것은 원본이 여기 없는 코드뿐이다.
  - 그중에서도 **코드를 제시하는 것이 기능을 장문으로 설명하는 것보다 효과적일 때**만 넣는다.
  - 예를 들어 내가 만드는 API를 부르는 클라이언트, 예시 요청, 사용자가 쓰는 설정, 커맨드라인 명령이 여기 해당한다.
- 중복된 내용이 여러 문서에 퍼져 있으면 안 된다.
  - SoT의 위치를 정하고, SoT가 아닌 곳에서는 링크를 건다.
  - 같은 규약이 두 곳에 있으면 설계 문서가 SoT다.
    - 실행하는 파일이 어긋나면 파일 쪽이 틀린 것이니 설계 문서에 맞춘다.
  - 설계 문서로 옮겨 적을 수 없는 것은 그 파일 자체가 SoT다.
    - 설계 문서에서는 링크만 건다.
    - 스키마, 락파일, 문법이 고정된 설정이 여기 해당한다.
  - 문서끼리 링크를 걸 때에는 참조 관계를 단순하게 유지한다.
    - 둘이 서로 참조하는 것은 괜찮지만, 셋 이상이 연결된 순환 참조는 만들지 않는다.
- 문서와 PR/MR에 경어를 쓰지 않는다.
