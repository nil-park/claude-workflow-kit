# 듀오 세션 작업

- 사용자가 이 방식으로 지시한 작업에만 적용한다.
  - 지시를 받기 전에는 기다린다.
  - 질문을 지시로 받거나 의도를 추론해 작업을 시작하지 않는다.
- 주 세션과 peer는 사용자가 터미널 두 개에 각각 띄운 Claude Code 세션이다.
  - peer는 `ListAgents`에 나타나는 세션이며, `Agent`로 만든 서브에이전트가 아니다.
  - 주 세션은 백그라운드 세션이나 서브에이전트를 새로 띄우지 않는다.

## 시작

- `ListAgents`로 peer를 확인한다.
  - peer가 없으면 사용자에게 터미널을 하나 더 열어 Claude Code를 실행해 달라고 요청한다.
- 작업 단위와 범위를 정하고, 현재 기준이 코드, 설계 문서, 외부 명세 중 어디인지 확인한다.
- 작업에 맞는 스킬의 원문을 읽는다.
  - 파일을 고치는 작업에는 `work-cycle`을 적용하되, 종료 조건은 아래 "클린 패스와 종료" 절을 따른다.
  - 문서에는 `docs-standards`, 코드에는 `coding-standards`를 적용한다.
  - `anti-claudeism`은 문서와 코드 모두에 적용한다.
  - 브랜치나 PR/MR을 다룰 때는 `git-workflow`를 적용한다.
- 주 세션의 출력 문체는 `fluent-korean` 지침을 따른다.
- 작업 전제를 사용자가 볼 수 있는 임시 디렉토리의 마크다운 파일 하나에 모으고, peer에게 그 경로를 준다.
  - 파일 이름에는 작업 주제를 넣는다.
  - 규모, 외부 환경, 언어와 런타임의 제약, 상위 명세와 다르게 정한 항목을 적는다.
  - 사용자 판정도 여기에 기록한다.

## 역할

- 주 세션이 설계 문서, 코드, 한국어 문구를 모두 쓰고 고친다.
- peer는 파일을 고치지 않고, 읽은 뒤 지적하거나 제안한다.
  - 지적은 지금 파일에 있는 결함이다.
    - 사실 오류, 규칙 위반, 모순, 후속 작업을 잘못 이끌 서술이 해당한다.
  - 제안은 설계, 표현, 구조를 더 낫게 바꿀 대안이다.
    - 결함이 아니므로 반영 여부는 주 세션이 정한다.
- 취합, 판단, 검증, 포매팅, 커밋, 브랜치와 PR/MR 조작은 주 세션이 한다.
  - 설계 단계에서는 임의로 커밋하지 않는다.
  - 구현 단계에서는 작업 단위로 커밋한다.
  - 완료를 보고한 뒤에는 사용자의 명시적 지시 없이 커밋하지 않는다.
- PR/MR 하나가 설계와 구현을 모두 포함한다.
- 결정 기록(`docs/decisions/`)은 사용자가 쓴다.
  - 주 세션과 peer 모두 결정 기록을 만들거나 고치지 않는다.
- 구현 단계에서 설계와 구현이 어긋나도 설계 문서를 임의로 고치지 않는다.
  - 어긋남이 실제 문제로 이어지는 조건과 확률을 적어 사용자에게 보고하고 판단을 받는다.
- 구현을 마치면 peer에게 한국어 검수를 따로 요청한다.
  - 대상은 주석, 문서, 화면 문구, 오류 메시지, 테스트 이름, 커밋 메시지, PR/MR 제목과 본문이다.
  - 화면 문구는 읽는 사람이 개발자가 아니라는 전제로 검수해 달라고 요청한다.
  - 문장을 고친 뒤에는 주석이 코드와 어긋나지 않는지 다시 확인한다.

## 지적과 제안을 다루는 기준

- 사용자 판정이 스킬의 기본값보다 우선한다.
- 지적과 제안을 그대로 받지 않는다.
  - 틀린 지적도 나오므로, 근거를 코드, 문서, 재현 경로에서 직접 확인한다.
  - peer가 제시한 대체 문구가 새 모순을 만들기도 하므로, 문서 전체와 코드에 대조한다.
- 주 세션이 반영 기준을 정하고, 기준에 맞지 않는 세부 사항은 반영하지 않는다.
  - 지적을 모두 받으면 문서는 비대해지고 코드는 오버엔지니어링된다.
  - 실제 오류이거나, 빠지면 후속 작업이 다른 방향으로 갈 위험이 있을 때만 반영한다.
  - 코드가 기준인 작업에서는 코드만 읽어도 알 수 있는 상세를 문서에 옮기지 않는다.
  - 문서가 기준인 작업에서는 회귀 위험과 폐기한 대안의 재채택 가능성이 모두 낮을 때만 규칙을 지운다.
  - 주석에도 같은 기준을 적용한다.
- 반영하지 않은 지적과 제안은 근거와 함께 전제 파일에 기록하고 peer에게 알린다.
- 진행 중에는 `work-cycle`이 정한 경우에만 사용자를 부른다.

## 클린 패스와 종료

- peer가 세 번 연속 `없음`을 회신하면 마무리한다.
  - `work-cycle`의 클린 패스 조건을 이 조건으로 대체한다.
  - 주 세션도 라운드마다 파일을 직접 읽지만, 자체 리뷰의 클린 횟수는 세지 않는다.
- 제안만 있고 지적이 없는 라운드도 클린으로 센다.
- 파일을 고치면 이유와 관계없이 연속 횟수를 0으로 되돌린다.
  - 지적을 반영한 경우, 제안을 반영한 경우, 주 세션이 스스로 결함을 찾아 고친 경우가 모두 해당한다.
- 파일이 바뀌지 않은 채 이어지는 라운드에는 리뷰 프롬프트에 앞 라운드와 다른 관점을 지정한다.
- 작업 범위 밖의 문제(예: 코드와 문서의 불일치)는 결함과 분리해 따로 기록한다.
  - 이후 리뷰 프롬프트의 "제외할 것"에 그 문제를 적는다.
- 라운드 기록은 하네스 스크래치패드에 저장한다.

## 최종 보고

- 바뀐 범위, 직접 정한 전제, 뒤집힌 판단, 실행한 검증과 생략한 검증을 적는다.
- 반영하지 않은 지적과 제안 중 사용자가 판단해야 할 것을 따로 모아, 각각의 근거와 함께 올린다.
- 전제 파일의 내용을 사용자에게 확인받는다.
  - 그중 개발할 때 알아야 할 것만 리포 문서로 옮긴다.
  - 옮길 위치는 `docs-standards`를 따른다.

## peer에게 보낼 프롬프트

- `<>`로 표시한 곳을 채워 `SendMessage`로 보낸다.
- 첫 프롬프트는 작업을 시작할 때 한 번 보낸다.
- 리뷰 프롬프트는 편집을 마칠 때마다 보낸다.
  - 주 세션이 편집하는 동안에는 리뷰를 요청하지 않는다.

### 첫 프롬프트

```markdown
너는 이 작업의 peer 세션이다. 나는 주 세션이고, 파일은 내가 모두 쓰고 고친다.
너는 내가 요청한 파일을 읽고 지적하거나 제안한다.

- 리포: <절대 경로>
- 작업: <작업 단위와 범위>
- 현재 기준: <코드 | 설계 문서 | 외부 명세>
- 작업 전제: <전제 파일의 절대 경로>
  - 여기 적힌 것은 되묻지 않는다. 전제 자체가 틀렸다고 볼 때만 근거를 들어 지적한다.

## 지킬 것

- **보고는 사용자가 아니라 나에게 `SendMessage`로 보낸다.**
- 파일을 고치지 않는다. 포매터, 린터, 커밋, 원격을 바꾸는 명령도 실행하지 않는다.
  - 코드와 원격 정보를 읽는 명령은 써도 된다.
- `Agent`로 서브에이전트를 띄우지 않는다.
- 판단 기준이 되는 스킬은 리뷰할 때마다 원문으로 확인한다. 요약이나 기억으로 대신하지 않는다.
  - 문서: `docs-standards`, `anti-claudeism`
  - 코드: `coding-standards`, `anti-claudeism`
- 파일은 처음부터 끝까지 읽는다. `grep`과 `sed -n`은 통독 전 탐색에만 쓴다.
- 출력 문체는 `fluent-korean` 지침을 따른다. 내 메시지와 전제 파일의 문체를 따라 하지 않는다.

## 회신 형식

- 지적이 없으면 첫 줄에 `없음`이라고 쓴다.
  - 제안만 있을 때도 첫 줄은 `없음`으로 쓰고, 제안은 그 아래에 적는다.
- 지적에는 위치, 근거, 영향을 적는다.
  - 재현되는 결함에는 입력이나 상태를 적는다.
  - 문장 결함에는 해당 표현을 인용한다.
- 제안은 지적과 나눠 `제안` 아래에 적는다.
  - 설계, 표현, 구조를 더 낫게 바꿀 대안을 제시한다.
  - 반영 여부는 내가 정한다.
- 라운드를 채우려고 지적이나 제안을 만들지 않는다.
- 전제를 넘어서는 방어 로직이나 설명을 더하자는 지적은 하지 않는다.
```

### 리뷰 프롬프트

```markdown
<파일 절대 경로>를 리뷰해라.

- 상태: <첫 리뷰 | 앞 라운드 뒤 수정함 | 앞 라운드 뒤 수정하지 않음>
- 이번 관점: <검토 범위와 관점. 수정하지 않았다면 앞 라운드와 다른 관점>
- 확정된 것: <다시 지적하지 않을 것>
- 제외할 것: <따로 기록한 작업 범위 밖의 문제 등>

보고는 사용자가 아니라 나에게 보낸다.
```
