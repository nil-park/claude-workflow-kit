# 작업 단계

작업은 네 단계로 진행한다.

1. 작업 단위 확정
2. 설계
3. 구현
4. 보고

**내가 구현을 명시적으로 지시하기 전에는 구현에 들어가지 않으며, "구현을 시작할까요?"라고 묻지도 않는다.**

## 1. 작업 단위 확정

- 내가 이슈 번호나 Jira 이슈 키를 주면 해당 이슈를 작업 단위로 삼는다.
- 다음 내용을 리포지토리의 임시 디렉터리에 정리한 뒤 확인받는다.
  - 예상 변경 범위와 분량
  - 내 지시에 명시되지 않았지만 작업에 필요한 전제와 가정
  - 설계 단계를 따로 둘 만한 규모인지
- **내가 명시적으로 "설계만" 또는 "구현만"이라고 지정하지 않는 한, MR은 설계와 구현을 모두 포함한다.**
- **브랜치를 만들기 전에 origin의 기본 브랜치(main/master)를 확인한다.**
  - MR은 이 기본 브랜치를 대상으로 연다.
- 브랜치를 만들어 push한다.
  - 브랜치 이름은 `<타입>/<슬러그>`로 짓는다(예: `chore/add-user-ssh-key`).
  - 이슈 번호나 Jira 이슈 키는 브랜치 이름에 넣지 않는다.
- **이 단계에서는 구현 코드를 한 줄도 쓰지 않는다.**

## 2. 설계

- 설계 문서는 리포지토리의 문서 디렉터리에 쓴다.
  - 리포지토리에 명시된 문서 규약이 있다면 철저히 지킨다.
  - 명시된 규약이 없다면 기존 문서에서 관례를 파악하고, 그 관례를 임시 디렉터리에 요약해 확인받는다.
- 이슈처럼 참고할 문서가 맥락을 빠짐없이 설명하고 있으면, 설계 문서를 고치면서 구현을 함께 진행할 수 있다.
  - 이때에도 나에게 먼저 확인받는다.
- 참고할 문서 없이 처음부터 설계하면, 설계를 확정하기 전에는 구현에 들어가지 않는다.
  - 전체 방향은 나와 대화하면서 정하고, 세부 내용은 네가 초안으로 작성한다.
- 구현 단계에 들어간 뒤에는 내 명시적인 지시 없이 설계 문서를 고치지 않는다.
  - 설계를 꼭 바꿔야 하면 바꿀 내용을 마크다운 문서로 써서 나에게 보고한다.
  - 바꿀 내용을 세 줄로 요약할 수 없으면 설계 자체에 문제가 있으므로 설계 단계로 돌아간다.
- 구현 전에는 코드와 설계가 어긋나 있는 것이 정상이다.
  - 다른 에이전트가 리뷰에서 이 차이를 지적하더라도, 그 지적을 근거로 MR 범위를 설계 전용으로 재해석하지 않는다.

## 3. 구현

- 변경을 작은 단위로 나눠 커밋한다.
- 커밋하기 전에 리포지토리의 가이드에 따라 린터, 포매터, 유닛 테스트 등을 실행한다.

## 4. 보고

- MR 제목과 본문을 최종 변경 내용에 맞춰 고친 뒤 완성본을 제시한다.
- 아래 항목이 있으면 보고한다.
  - 내 지시나 설계 문서에 근거하지 않고 임의로 가정한 내용
  - 예상하지 못한 문제 때문에 설계와 달라진 구현
- 보고할 항목이 셋 이상이면 그 내용을 리포지토리의 임시 디렉터리에 마크다운 문서로 정리하고, 문서 첫머리에 요지부터 적는다.
- MR은 Ready로 전환한다.
  - **머지는 내가 검토한 뒤에 직접 한다.**

# GitLab MR

- **MR 제목과 본문은 구현까지 완료된 최종 결과를 기준으로 작성한다.**
  - draft MR을 구현 전에 열더라도, "설계 문서 추가"나 "설계 단계"처럼 범위를 설계로 한정하는 표현을 넣지 않는다.
- 커밋 없이 브랜치만 push해도 MR을 열 수 있다.
  - draft MR은 작업 단위 확정 단계에서 브랜치를 push한 뒤 연다.

```
glab mr create --remove-source-branch --squash-before-merge \
  --target-branch "<origin 기본 브랜치>" --draft -a @me \
  -t "제목" -d "$(cat <본문 파일>)"
```

- 본문은 `glab mr edit`이 아니라 `glab mr update`로 고치고, Ready로 전환할 때에는 `glab mr update --ready`를 실행한다.

# 본문 작성 규약

- 본문에 넣을 것과 뺄 것은 리포지토리 규약을 확인해 따른다.
- 이슈 번호나 Jira 이슈 키는 기본 브랜치에 직접 커밋할 때만 커밋 메시지에 넣는다.
- 본문은 파일로 쓴다.
  - 여러 줄 텍스트를 명령줄에 직접 붙여 넣으면 이스케이프 실수가 생기기 쉽다.
  - `glab`은 `--body-file`을 지원하지 않으므로, 파일 내용을 `-d "$(cat <본문 파일>)"` 형태로 넘긴다.
