# 적용 대상

- 파일을 만들거나 고치는 작업이면 크기와 무관하게 이 사이클을 돈다. 내가 받는 것은 사이클을 완주한 완결성 있는 결과물이다.
  - 예를 들어 "CLAUDE.md 한 줄 고쳐줘"도 대상이다.
  - 설계는 스펙 문서를 작성하고, 작성한 문서를 대상으로 리뷰 라운드를 돈다.
  - 구현은 구현 변경분을 대상으로 리뷰 라운드를 돈다.
- 파일을 남기지 않는 작업은 대상이 아니다. 아래는 대상이 아닌 예시.
  - "장애 원인을 로그에서 찾아줘" (읽기만 한다)
  - "도커 이미지랑 볼륨 정리해줘" (파일을 고치지 않는다)

## git 리포지토리 밖의 파일

- `~/.claude/CLAUDE.md`, 홈 디렉터리의 스크립트, 시스템 설정도 대상이다. 되돌릴 git이 없으므로 같은 디렉터리에 미리 `.bak` 확장자의 사본을 만들어 수정에 대한 롤백이 가능하게 한다.
  - 리뷰 라운드가 보는 diff는 원본과 그 사본의 차이다.

## 도메인 판정

- 리뷰 기준은 도메인에 따라 달라지므로 작업 시작 전에 먼저 도메인을 판정한다.
  - 문서 개정 or 애플리케이션 코드 or 인프라 코드
  - 어떤 언어, 런타임, 프레임워크를 사용하는지
  - 클라이언트 or 서버 or 배치 작업
- 나와 합의한 작업 단위에서 유추해서 스스로 판단한다.

# 리뷰 라운드

- **서브 에이전트나 빌트인 스킬을 사용하지 않고 네가 직접 리뷰한다.** 리뷰 지적 사항에 대한 수정도 네가 직접 처리한다.
- **빈 라운드가 세 번 연속 나올 때까지 반복한다.** 지적이 나온 라운드는 카운트를 0으로 되돌린다. 상한은 없다. **클린 패스 연속 3회가 사이클의 종료 조건**이다.
- 문서 작성이나 변경에 대해서는 `workflow-core:docs-standards` 스킬에서 정한 기준에 따라 리뷰한다.
- 코드 작성이나 변경에 대해서는 `workflow-core:coding-standards` 스킬에서 정한 기준에 따라 리뷰한다.
  - 단 **네가 작성하거나 수정한 것이 무엇을 깨뜨렸는지 되짚는 것**은 매 라운드에서 확인한다.
  - 라운드마다 도메인에 적합한 리뷰 기준을 스킬에서 골라 2개를 선별해서 리뷰하되, 가능하다면 스킬이 커버하지 못하는 관점으로도 확인하려고 노력한다.
  - 리뷰 기준은 직전 라운드에서 이미 해결된 것은 선택을 피하되 서로 다른 기준이 낳는 회귀 루프는 반드시 감지해서 종합적인 해결 방안을 모색한다. 즉 이번 라운드의 기준만을 기계적으로 적용하지 말고 종합적인 밸런스를 파악하라는 의미.
- 대용량의 파일이 아니라면 `grep` 등으로 발췌해서 읽지 않고 되도록 **직접 전체를 읽어서 파악**한다.
- 라운드마다 나에게 보고하지 말고 `workflow-core:refs-scratch` 스킬에서 정한 규약에 따른 임시 디렉토리에 마크다운 문서로 기록한다. 라운드마다 문서를 남기거나, 기존 문서에 덧붙이는 방식으로 기록하되, 나는 주로 "보고" 단계에서 요약한 내용을 확인하고, 라운드 기록은 필요할 때만 참조한다.
- 라운드를 도는 중에 나를 부르는 경우는 셋뿐이다.
  - 설계를 바꿔야 풀리는 것이 나왔을 때
  - 작업 범위를 넓혀야 풀리는 것이 나왔을 때
  - 설계가 촘촘하지 않아서 너무 많은 가정을 해야 할 때
