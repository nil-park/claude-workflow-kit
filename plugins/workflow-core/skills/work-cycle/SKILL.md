# 작업 사이클

- 파일을 만들거나 고치는 작업이면 크기와 무관하게 이 사이클을 돈다. 내가 받는 것은 사이클을 완주한 결과물이다.
  - 예를 들어 "CLAUDE.md 한 줄 고쳐줘"도 대상이다.
- 파일을 남기지 않는 작업은 대상이 아니다. 아래는 대상이 아닌 예시.
  - "장애 원인을 로그에서 찾아줘" (읽기만 한다)
  - "도커 이미지랑 볼륨 정리해줘" (파일을 고치지 않는다)

## 단계와 리뷰 게이트

네 단계다. 1·2·4단계는 나와 대화하고, 3단계와 라운드는 자율로 돈다.

1. 작업 단위 확정
2. 설계
3. 구현
4. 보고

- 무언가를 써서 내놓는 단계는 그것을 대상으로 리뷰 라운드를 완주한 뒤에야 다음으로 넘어간다.
  - 설계는 스펙 문서를 작성하고, 작성한 문서를 대상으로 리뷰 라운드를 돈다.
  - 구현은 구현 변경분을 대상으로 리뷰 라운드를 돈다.
  - 1·4단계는 새로 쓰는 것이 없어 대체로 예외이지만, 작업 단위가 한두 문장이 아니라 복잡한 제약 사항을 명시해야 한다면, 이 역시 임시 문서를 작성하는 경우가 있고, 이때는 그 문서를 대상으로 리뷰 라운드를 돈다.
- 라운드를 어떻게 도는지는 아래 「리뷰 라운드」에 있다.

## git 리포지토리 밖의 파일

- `~/.claude/CLAUDE.md`, 홈 디렉터리의 스크립트, 시스템 설정도 대상이다. 되돌릴 git이 없으므로 같은 디렉터리에 미리 `.bak` 확장자의 사본을 만들어 수정에 대한 롤백이 가능하게 한다.
  - 리뷰 라운드가 보는 diff는 원본과 그 사본의 차이다.

# 작업 단계

## 1. 작업 단위를 확정한다

- 무엇을 바꾸는 작업인지 한 문장으로 되짚어 나에게 확인받는다.
- 도메인을 판정한다
  - 문서 개정 or 애플리케이션 코드 or 인프라 코드
  - 어떤 언어, 런타임, 프레임워크를 사용하는지
  - 클라이언트 or 서버 or 배치 작업
- 도메인 판정은 리뷰의 기준을 정하는 데 중요하며, 나와 합의한 작업 단위에서 유추해서 스스로 판단한다.

## 2. 설계

- 규모를 보고 스펙 문서를 쓸지 한 문단짜리 의도 진술로 갈음할지 제안한 뒤 확인받는다.
- 스펙 문서는 리포지토리의 문서 디렉터리에 쓴다. `workflow-core:docs-standards` 스킬에서 정한 규칙에 따라 작성한다.
- GitHub, GitLab, 또는 Jira 이슈 등 레퍼런스로 삼을 문서가 이미 모든 맥락을 빠짐없이 설명하고 있으면 설계 문서 수정과 구현 단계를 동시에 진행할 수도 있다. 단, 나에게 먼저 확인받는다.
- from scratch로 시작할 경우 설계가 확정되기 전에는 구현을 시작하지 않는다. 나와의 대화를 통해 큰 줄기를 잡고, 세부 내용은 네가 초안을 작성한다. 작성한 초안을 나에게 제시하기 전에 리뷰 라운드를 돈다.
- 구현 단계로 들어가면 되도록 설계 문서를 고치지 않는다. 불가피한 경우 마크다운 문서로 써서 나에게 보고하되, 세줄 요약이 불가능하면 설계 자체에 문제가 있는 것이므로 설계 단계로 돌아가야 한다.

## 3. 구현

- PR 또는 MR을 진행할 때는 작업 단위를 잘게 쪼개서 커밋하되, 커밋 단위에 대해서도 리뷰 라운드를 돈다.
- 커밋의 diff에 대해 빈 입력, 에러 경로, 잘못된 변수, 놓친 엣지 케이스 등 틀릴 수 있는 이유를 적극적으로 찾아본다. 맞다고 확인하는 것이 아니라 버그가 있다고 가정하고 확인한다.
- 설계 문서가 커버하기에는 작은 부분에 대해서 why가 필요하면 주석을 남기되 불필요한 주석은 최소화한다. 주석이 없어도 코드의 의도가 정확하게 이해된다면 주석을 남기지 않는다.
- 심볼의 이름을 신중하게 고른다.
- 타입 체커를 충분히 활용한다. 타입 체커가 잡아내는 문제를 함부로 억제하지 않는다. 타입 체커가 잡아내는 문제를 억제해야 한다면, 그 이유를 주석으로 남기거나, 빈번하게 발생하는 지점은 별도 문서로 챙겨서 링크를 건다.

## 4. 보고

- PR 또는 MR을 진행할 때는 제목과 본문에 드리프트가 없는지 여부를 체크해서 개정 후에 완성본을 제시한다.
- 내가 명시적으로 지시하거나 설계에 담지 않은 내용 중 임의로 가정한 것이 있으면 보고한다.
- 라운드에서 기각한 지적이 있으면 짧게 요약해서 보고한다.
- 제시할 항목이 3개 이상이면 마크다운 문서로 써서 보고한다.
  - 두괄식으로 내용을 요약한다. 최대한 간결하게 작성하려고 노력한다. 보고서도 리뷰 라운드의 대상이다.

# 리뷰 라운드

- `workflow-core:review-criteria` 스킬의 기준을 적용해 리뷰한다.
- **서브 에이전트나 빌트인 스킬을 사용하지 않고 네가 직접 리뷰한다.**
- 대용량의 파일이 아니라면 `grep` 등으로 발췌해서 읽지 않고 되도록 **직접 전체를 읽어서 파악**한다.
- **직전 라운드에서 네가 한 수정이 무엇을 깨뜨렸는지 되짚는 것**은 매 라운드에서 확인한다. 그 외에는 라운드마다 새로운 각도에서 리뷰하되 도메인에 적합한 리뷰 기준을 3개 정도 선별해서 리뷰한다. 리뷰 기준은 라운드마다 바뀔 수 있다.
- 리뷰에 대한 수정도 네가 직접 처리한다.
- **빈 라운드가 세 번 연속 나올 때까지 반복한다.** 지적이 나온 라운드는 카운트를 0으로 되돌린다. 상한은 없다. **클린 패스 연속 3회가 사이클의 종료 조건**이다.
- 라운드마다 나에게 보고하지 말고 마크다운 문서로 기록한다. 라운드마다 문서를 남기거나, 기존 문서에 덧붙이는 방식으로 기록하되, 나는 주로 "보고" 단계에서 요약한 내용을 확인하고, 라운드 기록은 필요할 때만 참조한다.
- 라운드를 도는 중에 나를 부르는 경우는 셋뿐이다.
  - 설계를 바꿔야 풀리는 것이 나왔을 때
  - 작업 범위를 넓혀야 풀리는 것이 나왔을 때
  - 설계가 너무 촘촘하지 않아서 너무 많은 가정을 해야 할 때

# 게이트와 기록

무엇에 리뷰 라운드가 걸리고, 그때 라운드 기록을 남기는지를 한자리에 모은다. 표에 없는 것에는 게이트가 걸리지 않는다.

| 대상           | 단계 | 게이트 조건                               | 라운드 기록   |
| -------------- | ---- | ----------------------------------------- | ------------- |
| 작업 단위 메모 | 1    | 제약이 복잡해 문서로 써야 할 때만         | 남긴다        |
| 스펙 문서      | 2    | 항상                                      | 남긴다        |
| 설계 후속 메모 | 3    | 걸리지 않는다 — 세 줄 규모다              | —             |
| 커밋 diff      | 3    | PR·MR로 진행할 때 커밋마다                | 남기지 않는다 |
| 구현 변경분    | 3    | 항상                                      | 남긴다        |
| 보고서         | 4    | 보고할 항목이 3개 이상이라 문서로 쓸 때만 | 남기지 않는다 |

- 게이트가 걸리는 곳의 종료 조건은 모두 같다 — 「리뷰 라운드」의 클린 패스 연속 3회다.
- 스펙 문서만 리포지토리의 산출물이라 커밋한다. 나머지는 작업 부산물이라 커밋하지 않는다.
- 작업 부산물을 **어디에 어떤 이름으로 두는지는 이 스킬이 정하지 않는다.** `workflow-core:refs-scratch` 스킬에서 정한 규약을 따른다.
