# GitLab 브랜치 + MR 워크플로

세 단계다. 1단계와 3단계는 나와 함께 하고, 2단계는 `work-cycle`에 넘긴다. 그 안에서 작업
단위와 설계는 나와 맞추고, 구현과 리뷰 라운드는 자율로 돈다.

**"MR 작성"이라고만 하면 1단계까지다.** 내가 명시적으로 시키기 전에는 구현을 시작하지
마라.

## 1. 브랜치와 draft MR

제목과 설명만 있는 draft MR을 연다. **이 단계에서 구현 코드를 한 줄도 쓰지 않는다.**

- **origin의 기본 브랜치(main/master)를 먼저 확인한다.** 그것이 `--target-branch`다.
- 브랜치 이름은 `<타입>/<슬러그>` — 예: `chore/add-user-ssh-key`. 이슈 번호나 Jira 키를
  브랜치 이름에 넣지 않는다. Jira 키는 MR 제목이, 이슈 링크는 MR 본문이 진다.
- **브랜치를 만들고 push한 뒤에** MR을 연다. 원격에 브랜치가 없거나 대상 브랜치와 커밋이
  같으면 `glab mr create`가 실패한다. 이 단계에는 담을 변경이 없으므로 빈 커밋으로 연다.
- 설명은 `.refs/mr-body-<브랜치-슬러그>.md`에 쓰고 경로로 넘긴다. 명령줄에 직접 붙이지
  마라.

```
glab mr create --remove-source-branch --squash-before-merge \
  --target-branch "<origin 기본 브랜치>" --draft -a @me \
  -t "GAI-123 제목" -d "$(cat .refs/mr-body-<브랜치-슬러그>.md)"
```

## 2. `work-cycle`에 넘긴다

설계·구현·리뷰는 `work-cycle`이 돈다. 이 스킬은 그 사이에 **커밋과 push 지점만** 정한다.

- spec doc이 확정되면 그것부터 커밋하고 push한다. 구현보다 먼저 올라가야 내가 설계를
  브랜치에서 볼 수 있다.
- 구현은 `work-cycle`이 리뷰 라운드를 완주한 뒤에 커밋하고 push한다. 라운드 중간의
  수정을 커밋으로 남기지 마라 — 회귀와 그 수정이 히스토리를 채운다.
- 사이클이 나를 부르면(설계 변경, 범위 확대, 반복되는 지적) 그대로 올려라.

## 3. ready 전환

`work-cycle`이 빈 라운드 3연속으로 끝났고 push까지 마쳤을 때만 전환한다.

```
glab mr update --ready
```

전환했다고 알리고 멈춘다. **머지는 내가 한다.**

## MR 설명 규약

- **현재 상태와 원하는 상태 사이의 델타**로 쓴다. spec doc이 있으면 그것이 원하는 상태를
  이미 말하므로, 이 MR이 그 간극의 어디를 메우는지만 적고 spec doc을 다시 설명하지 마라.
  spec doc 없이 간 작업이면 원하는 상태를 한 줄로 세우고 그 델타를 적는다.
- 25줄 안쪽을 목표로 한다.
- 체크박스(`- [ ]`)를 쓰지 않는다. 평범한 불릿을 쓴다.
- **MR이 진행되면 낡을 것을 빼라** — 정확한 테스트 개수, 줄 번호, "N개 중 M개 완료",
  "아직 미구현". 다음 push면 거짓이 된다. 이 MR이 무엇을 하는지 적고, 어디까지 왔는지는
  적지 마라.
- Jira 키는 **MR 제목에만** 넣는다. 개별 커밋 메시지에는 넣지 않는다. 기본 브랜치에 직접
  커밋할 때만 커밋 메시지에 넣는다.
- 아직 기본 브랜치에 없는 파일을 상대 경로로 링크하지 마라. 리뷰하는 동안 깨진다.

## MR 설명 수정

`glab mr edit`이 아니라 `glab mr update`를 쓴다. 본문은 같은 방식으로 `.refs/` 파일에
쓰고 `-d "$(cat ...)"`로 넘긴다.
